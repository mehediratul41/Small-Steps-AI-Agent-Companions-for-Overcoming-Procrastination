# Learn Small Steps by tracing it

Use synthetic development data. Read [system design](SYSTEM_DESIGN.md) for the map, then [code walkthrough](CODE_WALKTHROUGH.md) alongside the code. Each session below can be a separate short exercise.

1. **Run the application.** Follow [developer setup](DEVELOPER_MANUAL.md), then [user manual](USER_MANUAL.md). Open [main.dart](../outputs/frontend/lib/main.dart) and [app.dart](../outputs/frontend/lib/app/app.dart). Identify initialization, provider scope and router. Check whether the header says Demo or Connected development before interpreting a reply.
2. **Trace one task.** Create a synthetic Unicode task, edit it, complete and reopen it. Follow [state.dart](../outputs/frontend/lib/app/state.dart) → [repository.dart](../outputs/frontend/lib/data/repository.dart) → [main.py](../outputs/backend/app/main.py) → [db.py](../outputs/backend/app/db.py). Compare the fields with [API contracts](API_CONTRACTS.md). Explain why PATCH sends a complete task and why stale versions are rejected.
3. **Trace one chat request.** Select task context, send a synthetic message, and follow repository `chatWithId` into the backend chat route. Read [code walkthrough](CODE_WALKTHROUGH.md) for persona/context construction and stable request IDs. Run the isolated mock HTTP test before spending provider quota. Explain why a model reply cannot directly edit a task.
4. **Understand state and persistence.** Read [data and synchronization](DATA_AND_SYNC.md), then find the controller's persistence methods. Restart and compare local demo state with a connected server snapshot. Identify which pending records can be replayed and which mutations require the server.
5. **Understand identity.** Read [saved_connections.dart](../outputs/frontend/lib/data/saved_connections.dart) and backend ownership checks. Run `test/live_agent_accounts_test.dart`. Explain why switching linked DEV accounts changes tasks and history, and why a participant cannot freely switch conditions.
6. **Understand reminders and research logging.** Read [reminders.dart](../outputs/frontend/lib/data/reminders.dart), [researcher manual](RESEARCHER_MANUAL.md), and the device checklist in [troubleshooting](TROUBLESHOOTING.md). Distinguish scheduling, opening, explicit task initiation and focus start. State what evidence is missing for delivery and time-to-start.
7. **Make one small verified change.** Add or improve one ordinary UI translation using the localization instructions in [developer manual](DEVELOPER_MANUAL.md). Format, analyze and run the relevant test. Check both languages. Keep user-authored task text unchanged and avoid changing research prompts or instruments as a practice exercise.

After each session, explain the flow aloud: input → controller → repository → authenticated server → storage/provider → response → state → widget. Use [QA results](QA_AND_INTEGRATION_REPORT.md) to distinguish tested behavior from remaining assumptions.
